How to work with a coding agent in your terminal as a fast research assistant that needs clear instructions and close supervision. The first part says what it has in front of it that a chat window does not, and what you decide before it writes a line. The second part builds a small project from an empty folder: a scraper for the Dyson School’s Ph.D. placements page, a postdoc flag, a country column, and the moment the tool fills a column from memory. The third part writes the project’s CLAUDE.md and a read-only reviewer agent. Every step runs in RStudio’s Terminal tab.

Claude Code is the same Claude model as the chat window and Cowork, in a third harness: a program in your terminal that runs in one folder. The harness decides what the model can see and do. In a chat you paste context in and copy text out. Cowork reads and writes the files in a folder you connect and runs code in a sandbox on Anthropic’s servers, not on your laptop. Claude Code reads every file in the repository, edits files after showing each edit as a diff, and runs commands in your terminal: R, git, anything you could type there. That row is the difference that matters. The other two never touch your machine; this one does, which is why it asks before acting and why git is the safety net.

Two other kinds of tool are not this page’s subject. An inline tool such as GitHub Copilot in RStudio proposes the next few lines in the editor and sees only the open file. Terminal agents from other vendors work like Claude Code; the habits on this page transfer to them.

How Claude Code works: the loop inside the tool

Inside the tool runs a loop. Your prompt goes to the model together with a hidden system prompt and, if the folder has one, CLAUDE.md. The model writes text and nothing else; it cannot open a file or run a command itself. So it writes a request for a tool, and the harness carries it out: read a file, search the folder, run a command in the terminal, edit a file. The tool’s result comes back to the model as text, and the model decides the next step. That repeats until nothing is left to do; then you get a reply. Anthropic’s page How Claude Code works describes the same loop in three phases: gather context, take action, verify results. In today’s project the tool runs the script and fixes it when it fails; the third phase is still yours, because only you know the number the script must reproduce.

In manual mode the loop stops at every edit and at every command that changes something and asks you; reading is free. You can stop it too: Esc interrupts. Everything the model has in front of it at a given moment is its context: the system prompt, CLAUDE.md, your prompts, every file it read and every command output so far. A new session starts with an empty context. What carries over is what is on disk: the files, the commits, and CLAUDE.md.

What changes when a tool can edit your files

  • It can read any file in the repository. Nothing private goes in that folder.
  • Its edits land on disk, not in a chat.
  • It can run commands, including git.
  • It shows every edit as a diff before it lands. You accept or refuse.
  • Anything it reads goes to Anthropic’s servers. Restricted data stays out; develop on a public or synthetic sample.
  • What is right is still your call.

Four things change. It can read any file in the repository, so what it sees is not what you pasted but what is on disk. Its edits land on disk, not in a chat window. It can run commands, including scripts and git. Every edit appears as a diff before it lands; that diff is the one thing you must read. Anything it reads is sent to Anthropic’s servers for processing, so check your data use agreements before pointing it at confidential files; the practical workaround is to let it develop the code on a synthetic or public sample with the same structure, and to run the final code yourself on the restricted data. The verification is yours; the tool has no way to compare the number it produced with the number you meant.

You decide the question; it writes the code

  • It is strong at writing, refactoring and debugging code. It is weak at judging whether a specification answers your question.
  • Decide the estimand, the sample, the weights, the fixed effects and the clustering yourself. Then ask it to implement them.
  • Let it choose and it picks something plausible. Plausible is not the same as right.
  • A fact it did not read is a guess: a function’s arguments, a citation, a fact about the world. Check the documentation, the paper, the source.
  • You must be able to explain every line. Ask it to explain rather than write, and it becomes a tutor.

Claude Code is most useful when you treat it as a fast, capable research assistant that needs clear instructions and close supervision. It is strong at writing, refactoring and debugging code. It is weaker at judging whether a specification answers your question. So you own the identification and it owns the plumbing: decide the estimand, the fixed effects, the clustering and the sample restrictions yourself, then ask it to implement them. If you let it choose, it will pick something plausible, and plausible is not the same as right.

The same rule covers facts. It can misremember a function’s arguments, especially in less common packages; it can cite papers that do not exist or misstate what they found; it can fill a column with countries it never read anywhere. Check documentation and citations yourself, and treat any value it did not read from your data or your page as a guess until you have checked it. Today’s project shows this with a country column.

For students, understanding comes first. It is possible to produce working code without understanding it. The rule in this course is that you can explain every line of code in your analysis. Ask the tool to explain its code rather than only write it; that turns it into a tutor. A line you still cannot explain after the explanation is a line to replace with one you can.

The main risk is silent errors, not crashes

  • Code that fails is easy to fix. Code that runs and is wrong is the danger.
  • The usual shapes: a merge that drops or duplicates rows; NAs handled silently; a unit mismatch; an estimation call that differs a little from what you asked.
  • Three defenses: explicit checks, stopifnot() on row counts, unique keys and value ranges; estimators tried on simulated data with known parameters; the merge and the regression call read by you.
  • Git is the safety net: commit before each task, read the diff after it, git restore puts a file back.

Code that fails is easy to fix: the error names the line. Code that runs but is wrong is the real danger, and it is the common case with a tool that writes plausible code quickly. The usual shapes are a merge that drops or duplicates rows, NAs handled in a way you did not expect, a unit mismatch, and an estimation call that differs slightly from what you asked for: a different standard error, a sample restriction applied one step too late.

Three defenses, all yours. Ask for explicit checks, stopifnot() on row counts after a merge, on unique keys, on value ranges; the tool writes them well once you name the number. Test estimators on simulated data with known parameters before running them on real data; if the estimate does not recover the parameter you planted, the code is wrong, whatever the transcript says. And read the key lines yourself, the merges and the regression call above all.

Git is the safety net around all of it. Commit before each task, so the diff afterwards is exactly what the tool did. Review that diff. Claude Code edits many files quickly, and git is what lets you see what changed and roll back with git restore. If you do not use git yet, this tool is the best reason to start.

Small tasks, short sessions, a plan before code

  • One well-defined task per session: “build the county-year panel”, “write the event-study plot”. “Do the analysis” produces large vague code.
  • Performance drops as the context fills with old material. Start a fresh conversation between unrelated tasks (the /clear command).
  • Anything with a merge or a panel build: “Describe your approach before writing any code.” Read the plan; fix misunderstandings there, where they are cheap.
  • Conventions you would otherwise repeat go once into CLAUDE.md, a file it reads at every launch: base R only, never touch data/raw/, relative paths, a clean session, a master script, seeds, sessionInfo() saved with results.

Keep tasks small and sessions short. Everything the model has in front of it competes for its attention, and performance drops as the context fills with old material. Give one well-defined task per session, such as “build the county-year panel” or “write the event-study plot”, and use /clear between unrelated tasks. Large vague requests like “do the analysis” produce large vague code that nobody can check.

Plan before it writes code. For anything nontrivial, use plan mode (Shift+Tab cycles to it) or simply write “Describe your approach before writing any code.” Read the plan. Fix misunderstandings at that stage, when they are cheap. This habit matters most for data construction steps like merges and panel building, and today’s project shows what it would have caught.

Build reproducibility in from the start, as standing rules rather than reminders: a master script that runs the whole pipeline in order, package versions locked (renv is one way), a seed for anything stochastic, sessionInfo() saved with the results. The tool follows such rules reliably once they are written in CLAUDE.md, the file it reads at the start of every session; the sixth part of this page writes one for the project.

Two rules: a clean git state, and the diff over the transcript

  • Start from a clean git state. git status clean before the prompt; afterwards the diff is exactly what the model did.
  • Trust the diff, not the transcript. What it did, not what its replies say it did.
  • Commit before each task; read every diff before you commit; git restore puts a file back.

Rule one: start from a clean git state. git status prints nothing to commit, working tree clean before you type a prompt; then every line the diff shows afterwards is the model’s, and none is yours. Rule two: trust the diff, not the transcript. The transcript says what the tool claims it did. The diff shows what it did. When they disagree, the diff wins.

The project: the Ph.D. placements page, from an empty folder

  • The page: Recent job placements, Ph.D. in Applied Economics & Management. One table: year, name, position, organization. 109 rows when captured.
  • Four prompts, one task each: 1 start git; 2 read the table into a CSV (scraping); 3 flag the postdocs; 4 add each organization’s country. Then: where the countries came from.
  • The prompts tell the tool to run the script and fix it when it fails. You check every number against the page.
  • The folder: placements, no git yet. Once, in the Console: install.packages("rvest"), the R package that reads web pages.

The project is small and real. The Dyson School lists its recent Ph.D. placements on one public page as a table with four columns: year, name, position, organization. We scrape it into a CSV, add a column that flags postdocs, and add a column with the country of each organization. The page does not state the country, and that is the point of the third prompt.

Two things differ from a chat. The prompts tell the tool to run the script and fix it when it fails, so the tool is the loop; your job is the check, a number you count on the page before you believe the number on the screen. And everything starts from an empty folder: no repository, no script, nothing the tool did not write in front of you.

Launching Claude Code in manual mode

One line in the Terminal tab launches it in manual mode, where it reads freely but asks before every edit and every command that changes something. One task per prompt: the four parts

  • The goal: what the script must do, with names for its inputs and its output.
  • The mistake to avoid, named: the plausible wrong reading. Call it the failure mode.
  • The file to write, and where: code/<name>.R.
  • What not to do: no other files; no git, so that you read the diff and commit; and whether to run the script.
  • Prompt 1 had three of the four; Prompt 2, the scraper, has all four. Paste them; do not retype them.

A prompt that hands the tool one task has four parts, in any order. The goal: what the script must do, with names for what it reads and what it writes. The mistake to avoid, named: the plausible wrong reading a careful person could take; call it the failure mode. The file to write and where: which file, in which folder. What not to do: no other files; no git, so that the commit stays yours and the diff gets read; and whether to run the script or leave that to you. The fourth part is what keeps the diff small enough to read. Prompt 1 had a goal, a file and a “what not to do”; Prompt 2, the scraper, has all four. How much to ask for in one prompt: one task, one file

Too big to check Right-sized
“Do my analysis of the placements.” “Write code/placements.R: the table on the placements page, saved as data/placements.csv, four columns.”
“Make a report on placements.” “Add a column postdoc: TRUE when the position is a postdoc. Change nothing else.”
“Fix my script.” “The 2015 rows are missing; change the line that filters the years, nothing else.”

“Do my analysis of the placements” cannot be checked, because no number in the answer is one you could have worked out first. “Write code/placements.R: the table at that address saved as data/placements.csv” can: the page shows 16 rows for 2026, you count them in a few seconds, and the CSV must contain 16 rows for 2026 or the script is wrong. “Add a column postdoc” can too: the browser’s find box counts the spellings on the page.

So the unit to hand over is one task that writes one file and produces at least one number you can get yourself. A large job is several of these in a row, each checked before the next is sent, one per conversation. That is also why the third row of the table replaces “Fix my script” with a sentence naming the one thing that is wrong: it turns an open-ended request into a change whose size you know before you read the diff.

Three questions before you send a prompt

  1. Can you say in advance what a wrong answer would look like, and write that into the prompt?
  2. Can you work out one number of the answer yourself, from the page or from rows on your screen?
  3. Could you read the whole diff in five minutes?
  • Any no: the task is too big. Split it and send the first part.

Before pasting, three questions, and all three are about what you will do after the reply arrives.

Can you say in advance what a wrong answer would look like? Not “might it be wrong”, but what shape the error would take: rows dropped by a bad match, the countries averaged instead of the people, the other table on the page read instead of this one. You write that sentence into the prompt, which is the “mistake to avoid” part of the four. If no wrong answer occurs to you, you do not yet understand the task well enough to check it.

Can you work out one number of the answer yourself? One number is enough, from the page or from rows on your screen: 16 rows for the most recent year, 25 postdocs, two countries in Oceania. You get it before the script runs, so that the comparison afterwards is a comparison and not an impression.

The five-step delegation loop

Every delegation runs the same five steps. State the goal and the mistake you do not want (the failure mode). Delegate one task. Count by hand what it must return on a case small enough to check, on the page or from rows you can see, before anything runs. Run it and compare the printed value with the one on paper; if they disagree, read the diff, ask for a patch, run again. Then write the hand check into the script as a line that stops it when the value drifts (stopifnot()), so the next run checks itself. The value on paper comes from the data, not from a guess; that is what makes step 4 a comparison and not an impression.

This loop wraps the loop inside the tool. The tool gathers context, acts and checks its own result; you decide what right means and check it once more from outside. Anthropic’s best practices for Claude Code give the same advice in their own words: state verification criteria in the prompt (an example input and its expected output), scope the task to one file and one scenario, describe the symptom and what fixed looks like when asking for a fix, and, in the list of common failures, “If you can’t verify it, don’t ship it.” The five steps are that advice arranged for a novice who runs the script and reads the diff in person.

Subagents: a second Claude with its own context

  • A subagent is a separate conversation the tool starts for one task: its own empty context, its own tool list, CLAUDE.md included. It returns a report, not its working.
  • When: reading many files, so your context stays small; an independent review of a diff or a rule, so the checker is not the thing being checked.
  • One line: Use a subagent to review code/x.R against this rule: ... Report what it says. Do not edit anything.
  • Permanent: a file in .claude/agents/, like CLAUDE.md: a name, a description, the tools it may use, then its instructions.

A subagent is a second conversation that the tool starts for one task and closes when the task is done. It begins with an empty context: the task, CLAUDE.md, and nothing from your conversation, not the files already read, not the prompt that wrote the code. It has its own list of tools, which can be shorter than the main conversation’s. When it finishes, its report comes back into your conversation as text; its reading and its intermediate steps stay in its own context and are gone.

Two uses fit this course. The first is reading: a task that opens many files fills your context with their contents, and everything the model has in front of it competes for its attention; a subagent reads them in its own context and reports a summary. The second is review: a reviewer that did not see the conversation that produced the code judges the code on its own terms. That is the rule from the check section, the checker is not the thing being checked, applied inside the tool. The docs recommend the same step before treating a task as done, a review of the diff in a fresh context, and warn that a reviewer asked to find gaps will report some even when the work is sound; ask for gaps that affect correctness, not style.

Two ways to use one. The one-line way needs no setup: “Use a subagent to review code/x.R against this rule: … Report what it says. Do not edit anything.” The tool starts a general-purpose subagent with that task. The permanent way is a file in .claude/agents/ at the repository root, committed like CLAUDE.md: a name, a description of when it applies, the tools it may use, then its instructions in plain prose. The tools: line is a fence. A reviewer allowed only Read, Grep and Glob cannot edit a file whatever its instructions say. You call it by name in a prompt. The next section shows one.

A subagent is one more model call, with its own cost, and its report is a claim like any transcript: the line it quotes is what you check.

Tasks not to give Claude Code

  • Outputs you cannot check by hand.
  • Facts it did not read: a country, a citation, a function’s arguments.
  • Restricted data. It sends what it reads to Anthropic’s servers: develop on a public or synthetic sample, run the final code yourself.
  • Questions that do not touch the repository. Use a chat.
  • Long stretches without reading: accept-edits mode, until reading diffs is a habit.

Five kinds of work do not belong in it. Outputs you cannot check by eye or by hand; it will produce a plausible number in a script that runs. Facts it did not read: a country, a citation, the arguments of a function in a package it half remembers; check the page, the paper and the documentation yourself. Restricted data: anything it reads is sent to Anthropic’s servers, so check the data use agreement, let it develop the code on a public or synthetic sample with the same structure, and run the final code yourself on the real files. Questions that do not touch the repository; open a chat instead. Long stretches without reading; accept-edits mode exists, and it is not for the weeks in which reading diffs becomes a habit.

If a model ever produces a value inside a script rather than writing the script, five more duties apply. Write down the model and its version (pin it). Set its randomness, the temperature, to zero. Call the model once and reuse the saved replies on later runs (cache them). Save every raw reply to a file and commit it, not only the label you took from it. Write the model and the prompt in the README. If you cannot do all five, use a rule you can write down instead.

The five questions for any diff

# Question
1 Files: only the ones you named? (git status)
2 What was deleted: did you ask for each red line to go? Read these first.
3 The line that does the work: does it do what you asked, and only that?
